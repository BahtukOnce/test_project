# Красный свет — зелёный свет

Четвероногий робот учится добегать до финиша и замирать на красный свет.
Никакой готовой походки нет: в начале обучения это дёргающаяся куча палок,
которая падает на первом шаге. Ходьбу, торможение и умение стоять смирно
агент собирает сам из проб и ошибок.

Реализация на **MuJoCo** (физика) и **PPO** из stable-baselines3 (обучение).
Всё считается на процессоре, видеокарта не нужна, монитор тоже — рендер
идёт через программный OpenGL, поэтому это спокойно живёт на голом сервере.

---

## Как это устроено

Никакого обучающего набора данных нет. Есть петля, которая крутится
миллионы раз:

```
   ┌──────────────────────────────────────────────────┐
   │                                                  │
   ▼                                                  │
[Физика] ──наблюдение(32)──> [Нейросеть] ──моменты(8)──> [Физика]
 MuJoCo                       256x256                     считает
                                                          награду
   │                                                        │
   └─────────────────── награда ────────────────────────────┘
```

### Что агент видит — 32 числа

| Что | Сколько | Зачем |
|---|---|---|
| высота корпуса | 1 | понять, что падает |
| ориентация (кватернион) | 4 | понять, что перевернулся |
| углы 8 суставов | 8 | где сейчас ноги |
| линейная и угловая скорость | 6 | куда и как быстро летит |
| скорости суставов | 8 | как быстро двигаются ноги |
| **какой сейчас свет** | 1 | 1 = зелёный, 0 = красный |
| **сколько до переключения** | 1 | чтобы успеть затормозить заранее |
| сколько осталось на торможение | 1 | «окно», пока кукла разворачивается |
| порог вылета | 1 | насколько строгий сейчас судья |
| расстояние до финиша | 1 | сколько ещё бежать |

Ключевое здесь — «сколько до переключения». Без этого числа агент физически
не может остановиться вовремя: тело инерционное, тормозить надо заранее.

### Что агент делает — 8 чисел

Крутящий момент на каждый сустав, от −1 до 1. Управление на 20 Гц.
Никаких команд вроде «шагни левой» — только сырые усилия на моторы.

### За что награда

| Ситуация | Награда |
|---|---|
| зелёный свет | `+1.0 × скорость вдоль коридора` (не выше 4 м/с) |
| красный, окно торможения | `+2.0 × (насколько сбросил скорость)` |
| красный, стоит смирно | `+0.3 × (1 − скорость/порог)` |
| красный, поехал | **`−100` и конец эпизода** |
| каждый шаг на ногах | `+0.6` |
| каждый шаг | `−0.3` (штраф за время) |
| каждый шаг | `−0.1 × сумма квадратов моментов` |
| финиш | `+300` |
| упал или перевернулся | `−20` и конец эпизода |

Веса подобраны так, чтобы «стоять на месте весь эпизод» было **хуже**, чем
дойти до финиша, но **лучше**, чем нестись напролом и вылететь:

| стратегия | награда за эпизод |
|---|---|
| дойти до финиша | **≈ 1195** |
| простоять весь эпизод столбом | ≈ 400 |
| нестись, не глядя на светофор | ≈ 35 |
| упасть на старте | ≈ −12 |

Эти числа — не украшение, их надо пересчитывать после каждой правки весов
(скриптом из раздела «Типичные грабли»). В первой версии этого проекта
штрафа за время не было, и «стоять столбом» давало 836 против 826 за финиш:
агент, честно максимизируя награду, был обязан замереть на старте и
простоять весь эпизод. Формально он прав — ошибка была в постановке задачи.

Это и есть та самая работа, на которую в подобных проектах уходит больше
всего времени: не написать обучение, а объяснить агенту, чего от него хотят.

### Почему обучение идёт в два этапа

Учить ходьбе и правилам светофора одновременно почти безнадёжно: агент
вылетает раньше, чем успевает сделать шаг, и не получает никакого сигнала
о том, что ходьба вообще бывает.

1. **`--stage walk`** — светофора нет, есть только пустой коридор.
   Задача: научиться перемещать тело вперёд и не падать.
2. **`--stage game`** — берём готовую походку и включаем светофор,
   постепенно ужесточая правила (curriculum):

| Параметр | В начале | В конце |
|---|---|---|
| длина зелёного | 4.5–7.0 с | 1.8–3.5 с |
| длина красного | 1.0–1.8 с | 2.2–4.0 с |
| окно на торможение | 1.10 с | 0.35 с |
| порог «ты пошевелился» | 1.60 м/с | 0.30 м/с |

Сложность растёт линейно за первые 60% второго этапа (`--curriculum-frac`).

## Установка на сервер

Ubuntu/Debian, права sudo нужны только для системных библиотек рендера:

```bash
git clone <репозиторий>
cd red_light_green_light
./setup.sh
```

Если скрипт не подходит, то же самое руками:

```bash
sudo apt-get install -y python3-venv libosmesa6 libosmesa6-dev libgl1-mesa-dri
python3 -m venv .venv
./.venv/bin/pip install torch --index-url https://download.pytorch.org/whl/cpu
./.venv/bin/pip install -r requirements.txt
MUJOCO_GL=osmesa ./.venv/bin/python selfcheck.py
```

`selfcheck.py` за минуту проверяет импорты, сборку сцены, API среды, рендер
без монитора, кодирование видео и короткий цикл обучения. Если он зелёный —
всё остальное заработает.

> **Про torch.** Обязательно ставить CPU-сборку с отдельного индекса.
> Обычный `pip install torch` тянет ~2.5 ГБ CUDA-библиотек, которые на
> сервере без видеокарты просто занимают место.

> **Про `MUJOCO_GL`.** Скрипты сами выставляют `osmesa` — это программный
> рендер, он не требует ни монитора, ни видеокарты. Если на сервере есть
> GPU с драйверами, можно поставить `MUJOCO_GL=egl`: рендер будет быстрее.

## Запуск

```bash
# Этап 1: учимся ходить (~50 минут на 4 ядрах)
./.venv/bin/python train.py --stage walk --steps 4000000 --out runs/walk

# Этап 2: учимся играть со светофором
./.venv/bin/python train.py --stage game --steps 4000000 --out runs/game --init runs/walk

# Оценка: прогнать 50 эпизодов и посмотреть статистику исходов
./.venv/bin/python evaluate.py --model runs/game --episodes 50

# Видео с результатом
./.venv/bin/python record.py --model runs/game --out demo.mp4 --episodes 4

# Графики обучения
./.venv/bin/python plot_progress.py runs/walk runs/game --out progress.png
```

На сервере запускать лучше под `tmux`, чтобы обучение пережило обрыв ssh:

```bash
tmux new -s rlgl
./.venv/bin/python train.py --stage walk --steps 4000000 --out runs/walk
# Ctrl+B, потом D — отцепиться; tmux attach -t rlgl — вернуться
```

Обучение можно прервать по Ctrl+C — модель и статистика нормализации
сохранятся, видео с такой модели снимется.

### Какая модель сохраняется

В папке этапа появляется два набора файлов:

| Файл | Что это |
|---|---|
| `best_model.zip` + `vecnormalize_best.pkl` | **лучшая** модель по честной оценке |
| `final.zip` + `vecnormalize.pkl` | последняя модель на момент конца обучения |

`record.py` и `evaluate.py` сами берут лучшую, если она есть.

Разница между ними не косметическая. Политика PPO умеет **деградировать
после пика**: на этой задаче агент выходил на ~680 награды к 2.3 млн шагов,
а к 5 млн скатывался до 414. Если сохранять только финальную модель,
половина работы уходит в мусор.

Отбор идёт по **детерминированной** оценке (`EvalCallback`, 12 эпизодов
каждые 100 тыс. шагов), а не по средней награде на обучении. Это важно:
на обучении действия берутся из распределения со случайным разбросом, и
эта награда плохо предсказывает поведение готовой модели. На этом проекте
пик тренировочной награды пришёлся на 2.3 млн шагов, а по честной оценке
лучшим оказался чекпоинт на 4 млн — 53% финишей против 17%.

Оценочная среда всегда работает на **финальной** сложности, даже пока
curriculum ещё разогревается. Иначе рекорд, поставленный на лёгких
правилах, не побить никогда.

### Сколько это занимает

Замер на этой машине: **~1250 шагов симуляции в секунду на 4 ядрах**
(4 параллельные арены). Отсюда оценки:

| Ядер | Арен (`--n-envs`) | 4 млн шагов |
|---|---|---|
| 4 | 4 | ~55 мин |
| 8 | 8 | ~30 мин |
| 16 | 16 | ~15 мин |

Оба этапа по 4 млн — это примерно два часа на 4 ядрах. Масштабируется почти
линейно по ядрам, так что если на школьном сервере их много — ставьте
`--n-envs` по числу ядер.

### Что смотреть в логах

```
| rollout/ep_rew_mean     | 412    |   средняя награда за эпизод — должна расти
| outcome/finished        | 0.61   |   доля эпизодов с финишем
| outcome/eliminated      | 0.22   |   доля вылетов за движение на красный
| outcome/fell            | 0.05   |   доля падений
| curriculum/difficulty   | 0.83   |   текущая строгость правил
```

Нормальная картина: на первом этапе `fell` падает с 1.0 почти до нуля,
`best_progress` растёт. На втором `eliminated` сначала подскакивает
(включили светофор), потом снижается, `finished` растёт.

## Что можно покрутить

**Награды** — константы в начале класса `RedLightGreenLightEnv`
(`W_FORWARD`, `R_ELIMINATED`, `R_FINISH` и прочие). Это то место, где
на практике проводится больше всего времени.

**Сложность** — пары «значение при difficulty=0 → значение при difficulty=1»
там же: `GREEN_MIN`, `RED_MAX`, `GRACE`, `MOVE_THRESHOLD`.

**Длина дистанции** — `FINISH_X` в `arena.py` (по умолчанию 25 метров).

**Тело агента** — функция `_leg()` в `arena.py`. Можно добавить ног, удлинить
голени, поменять силу моторов (`gear` в блоке `<default>`). После правок
обязательно переучивать с нуля: старая политика рассчитана на старое тело.

## Типичные грабли

Сначала общий совет: когда обучение идёт, а результата нет, **не крутите
гиперпараметры PPO**. Почти всегда дело в награде или в условиях конца
эпизода. Разложите награду обученной модели по компонентам — это занимает
пять минут и сразу показывает, что происходит:

```python
# что реально приносит и отнимает очки у обученной модели
comp = dict(alive=0.0, time=0.0, ctrl=0.0, forward=0.0)
# ... прогнать несколько эпизодов, накапливая каждое слагаемое отдельно,
#     и поделить на число шагов
```

**Агент обрывает эпизоды прыжком.** Реальный случай из этого проекта: на
первом прогоне 99% эпизодов кончались исходом «упал», а агент не падал —
он подпрыгивал. Верхняя граница «здоровой» высоты стояла на 1.0 при старте
корпуса на 0.75, и любой нормальный прыжок засчитывался как падение.
Диагноз занял пять минут: высота корпуса в момент конца эпизода во всех
восьми тестовых забегах была 1.00–1.06, то есть ровно на границе.
Лечение — поднять верхнюю границу до 1.35 и отдельно проверять переворот
корпуса, а не одну высоту. **Условия конца эпизода — такая же часть
постановки задачи, как награда, и ошибаются в них не реже.**

**Штраф за моторы съедает награду за движение.** Там же: штраф за усилия
давал −1.22 за шаг при награде за скорость +1.53. Агент был вынужден
выбирать между «двигаться резко» и «не двигаться», и ровной походки
в этом коридоре не существовало. Снизил вес штрафа в пять раз.

**Награда росла, а потом поехала вниз.** Это нормальное поведение PPO,
а не поломка. Лечится затуханием learning rate (`--lr-schedule linear`,
включено по умолчанию), ограничением на шаг политики (`--target-kl`)
и — обязательно — сохранением лучшей модели, а не последней.

**Агент нашёл дыру в награде.** Классика: научился падать вперёд, потому что
это быстрее ходьбы, или прыгать на месте у самого финиша. Лечится не кодом
обучения, а формулой награды — добавьте штраф за то поведение, которое
считаете жульничеством.

**Агент просто стоит.** Значит, «стоять» выгоднее, чем «идти». Поднимайте
`R_FINISH` или `W_FORWARD`, снижайте `W_HEALTHY`.

**Второй этап ломает походку.** Слишком резкий curriculum. Увеличьте
`--curriculum-frac` или начните с `--difficulty-start 0`.

**Чёрные кадры в видео.** Не подхватился OSMesa. Проверьте
`MUJOCO_GL=osmesa` и что стоит `libosmesa6`.

**Обучение идёт, а награда не растёт вообще.** Проверьте, что подхватился
`vecnormalize.pkl` предыдущего этапа — без нормализации наблюдений PPO на
задачах с физикой учится заметно хуже.
